# Hamilton quirk register

Every place fnloom deliberately differs from Apache Hamilton 1.90.0, what it does instead, and the test that pins it.
fnloom fixes Hamilton's quirks by default, but each change needs a reason that holds for any user, not just one
workload.

!!! tip "Just moving code over?"

    [Coming from Hamilton](from-hamilton.md) summarises the rows that affect your code. This page is the full
    reference.

**What the dispositions mean:**

- **KEEP**: fnloom does what Hamilton does.
- **FIX**: deliberately different. Rows marked *Planned* describe a feature fnloom doesn't have yet.
- **REFUSE**: Hamilton silently accepts something dubious; fnloom raises.
- **DROP**: not carried over.
- **DEFER**: to be decided later.

**Evidence.** The behaviours below were first reported by an earlier investigation (2026-10-22) against Hamilton 1.90.0
and partly confirmed by reading its source. Rows Q4, Q5, Q6, Q7, Q10, Q11 to Q13, Q16, Q19, Q21 to Q48, Q50 to Q117
have differential tests in `tests/differential/test_deliberate_differences.py`, each marked `deliberate("<id>")`, that
assert Hamilton's behaviour and fnloom's side by side. Q23 is also covered by fnloom-only
tests (`tests/test_hooks.py`, `tests/test_binding.py` and the executor's unit tests), Q3 by `tests/test_driver.py`,
and Q49, a KEEP row, by `tests/test_caching.py`. Every other row is not yet re-run for this repository and becomes a
differential test before it is relied on. Source line numbers are deliberately omitted.

| ID | Hamilton behaviour | Disposition | fnloom behaviour |
|---|---|---|---|
| Q1 | Ships no `py.typed`; decorator `__call__` is unannotated, so decorated functions lose their signature for type checkers. | FIX | Typed package with `py.typed`; decorators return the function typed as itself. |
| Q2 | No public graph-inspection API; callers reach into `Driver.graph`, `FunctionGraph` and `Node` internals. | FIX | `Driver.nodes`: a read-only mapping, sorted by name, of a frozen `NodeView` per node and input, with its name, resolved type, dependencies, `is_input`, origin function, module, params, tags and docstring. The node's own callable is not exposed: a prepared plan replaces the replay it was used for. |
| Q3 | Every `execute` re-walks the subgraph, re-validates inputs and the executor, and generates a run id. | FIX | Compile once per (outputs, input names, override names); `prepare(...)` returns a reusable plan and `execute` uses it, keeping the 128 most recently used plans per driver. |
| Q4 | An input name that is not an input of the graph is accepted silently. | REFUSE | `ValueError` naming the culprit. |
| Q5 | A misspelled `overrides` key is ignored. | REFUSE | `ValueError`. |
| Q6 | A bare `str` passed as `final_vars` is split into one output per character. | REFUSE | `TypeError`. |
| Q7 | An `overrides` key naming an input is honoured when that input is also supplied and refused ("Required input … not provided") when it is not. | FIX | Pass-through: an override may name any node, input or derived; it beats a supplied input and satisfies a missing one. |
| Q8 | The order in which inputs are listed is not specified. | FIX | One deterministic order everywhere: listing APIs are sorted by node name; a result dict is in requested order, each output once (first occurrence), as in Hamilton. |
| Q10 | Edge and input type checks can only be switched off together, by an adapter (`NoEdgeAndInputTypeChecking`) that also changes other behaviour. | FIX | Edge checks on at build by default; input and override checks on by default; `Builder.without_input_type_checks()` turns off only those, and a mismatched edge still fails the build. Edge checks are turned off apart, for every edge or per consumer, by `without_edge_type_checks` (Q149). Pinned by `test_q10_opt_out_is_explicit`, and by `tests/test_type_checks.py`. |
| Q11 | `AsyncDriver` defaults to a pandas DataFrame result; the sync `Builder` defaults to a dict, and `async_driver.Builder` gives a dict with its keys sorted, whatever order they were requested in. | FIX | Dict everywhere: `AsyncDriver.execute` returns what `Driver.execute` does, each output once, in the order first requested. |
| Q12 | `async_driver.Builder.build` is async, so it cannot be cached the usual way. | FIX | Construction is always synchronous: `Builder.build_async()` returns the `AsyncDriver` itself, and only `execute` and `AsyncPreparedPlan.run` are coroutines. `prepare` is synchronous too. |
| Q13 | `AsyncDriver` uses `asyncio.iscoroutinefunction`, deprecated and scheduled for removal in Python 3.16: on 3.14 every node it runs warns `DeprecationWarning`. | FIX | `inspect.iscoroutinefunction`: no warning, and nothing to break on 3.16. |
| Q14 | Extension autoload imports heavy libraries (xgboost, sklearn, …) on `import hamilton` unless disabled by an environment variable. | DROP | No autoload. |
| Q15 | Every failed `execute` logs a community-promotion banner at ERROR level. | DROP | No banner. |
| Q16 | F17: the shipped cache re-hashes source on every execute, so a hit can cost more than recomputing. | FIX | Code versions are made once, at build, from code objects rather than source: a run reads no code, so rebuild the driver after editing it. |
| Q19 | `Driver.execute` returns different types depending on result builder and adapters. A result builder gets the outputs in request order, inputs and overrides requested as outputs included, and after-graph gets its built result. A builder that raises fails the run, and after-graph gets the raw dict. `raw_execute` skips the builder and fires every hook. The `AsyncDriver` silently drops a `ResultBuilder`. | FIX | `execute` returns a dict on both drivers, unless `Builder.with_result_builder(build)` sets a callable. `build` gets the raw outputs as a dict in request order, inputs and overrides requested as outputs included, as in Hamilton. `execute`, `PreparedPlan.run` and their async forms return what it returns. `Builder`, `Driver`, `AsyncDriver` and both plans take its type as a parameter that defaults to `dict[str, object]`, so a type checker sees the built type. `RunEnd.results` is always the raw dict. A builder that raises fails the run: `after_run` gets `ok=False`, its error and the raw `results`, as in Hamilton. `Driver.raw_execute` and `PreparedPlan.run_raw`, with their async forms, fire every hook and skip the builder, as Hamilton's `raw_execute` does. The `AsyncDriver` uses the builder. An output that is absent (Q135) is `fnloom.ABSENT` in the result dict, and a builder gets it as any other value; `frame()` refuses it with a `ValueError` naming it, since a column can't be absent. See [Result builders](running.md#result-builders). |
| Q20 | Depending on the package pulls in the whole runtime and its dependencies. | FIX | No required dependency beyond the interpreter. |
| Q21 | An adapter implementing the input-check hook **replaces** Hamilton's default check rather than adding to it: one whose `validate_input` returns `False` refuses a correct `x=1`, and one returning `True` lets `x="s"` reach the node. `None` passes whatever the hook says. The edge check is OR'ed with the default, so an adapter can only loosen an edge. | FIX | `Builder.with_value_check(check)` adds a check, cumulative with others: a value passes when the default check passes, or else when any custom check returns a true value for `(declared_type, value)`. A custom check is called only for a value the default refuses, so a value that fits costs nothing more, and it can admit but never refuse. It applies to inputs, overrides, extracted fields, output checks (Q87) and `validate`, never to edges, which compare types (Q10). An exception it raises is raised as it is. See [Type checks](running.md#type-checks). |
| Q22 | Override values bypass type checking and fail inside the node, or flow on as the wrong type. | FIX | Override values are checked against the node's declared type, like inputs, and a mismatch is a `ValueError` before any node runs. `Builder.without_override_type_checks()` turns off only the override checks, keeping input checks on (`without_input_type_checks()` turns off both). Pinned by `test_q22_override_type_checked`, and by `tests/test_type_checks.py`. |
| Q23 | A hook that raises aborts the run and skips the other adapters' hooks for that event. A raising before-graph hook skips after-graph too. A raising after-node or after-graph hook masks a node's error, which survives only as the hook error's `__context__`. | FIX | Every hook sees an event before its errors are raised. An error in `before_run` stops the run, and `after_run(ok=False)` still fires. One in `before_node` stops it before the node is called, and that node gets no `after_node`, as in Hamilton. One in `after_node(ok=True)` stops it and discards the node's value; one in `after_run(ok=True)` replaces the result, as in Hamilton. One error is raised as itself. Several are one `ExceptionGroup`: the node's own exception first, if a node failed, then the hook errors in event order, and within an event in hook order. A node's error is never masked. See [Hooks](hooks.md#a-hook-that-raises). |
| Q24 | Two adapters cannot implement the same lifecycle method, such as `do_build_result` or `do_node_execute`: two result builders are a `ValueError` at `build()`, naming the method, not the adapters. Hooks and validators layer. | KEEP / FIX | KEEP for the result builder: a second `with_result_builder` is a `ValueError` naming both builders, raised by the call rather than at `build()`. Hooks layer too (Q84). Node wrappers compose as an ordered chain, any number per driver (Q111). |
| Q25 | The graph walk is recursive, so a chain of about 1,000 dependent nodes raises `RecursionError` (verified at 1,000 and 5,000 on 1.90.0). | FIX | No recursion over graph depth anywhere; a 5,000-node chain runs. |
| Q26 | Execution order follows a recursive depth-first walk from the requested outputs, so it depends on the order the outputs are listed in and on parameter order, and it is visible to hooks and side effects. | FIX | Topological order with ties broken by node name, independent of output order. |
| Q27 | A dependency cycle is not detected up front: the recursive walk overflows and raises `RecursionError`. | FIX | `ValueError` naming the cycle, raised by `Graph::build`, that is by `fnloom.build` and `Builder.build`, before any request. |
| Q28 | `what_is_upstream_of` and `what_is_downstream_of` return `HamiltonNode` objects. | FIX | The same nodes, the named ones included, as sorted names; `Driver.nodes[name]` gives each one's typed view (Q2). |
| Q29 | A positional-only, `*args` or `**kwargs` parameter is accepted and treated as an input of that name. | REFUSE | `ValueError` at build: fnloom calls a node with one keyword argument per parameter name, and none of these kinds binds such an argument as a plain parameter. |
| Q30 | `final_vars` given functions maps each to its `__name__`, blindly: a `@parameterize` function becomes a name no node has, a forged function is accepted, and a function of a submodule is refused. | FIX | A function means the node it makes in this driver, matched by identity with the node's origin, never by name. A plain function is its node and an `@extract_*` function its producer. When several nodes share the function (an alias `alias = base`, or a row named like it), the one named like the function is its node. Otherwise, such as for a `@parameterize` one, it is a `TypeError` listing its rows. A function no node comes from (another module, an unselected `@config` variant, a lambda) is a `ValueError`. Works in `execute`, `prepare` and both drivers; the result is keyed by name. Every culprit of a request is listed once, sorted, in one message: a `TypeError` if any is malformed, else a `ValueError`. Pinned by the `test_q30_*` differential tests, which also pin Hamilton's side, and by `tests/test_validate.py`. |
| Q31 | `execute(final_vars, overrides, display_graph, inputs)` takes `overrides` second, so a positional mapping is read as overrides. | FIX | `inputs` and `overrides` are keyword-only on `execute`, `prepare` and `PreparedPlan.run`; a positional mapping is a `TypeError`. |
| Q32 | An `async def` or generator function is accepted as a node, and the sync driver returns the un-awaited coroutine or the generator object as its value. | REFUSE | `ValueError` at build naming the function: calling these does not run the body to a value. For an `async def`, `build()` says to use `build_async()`, whose driver awaits it; a generator, sync or async, is refused by both. |
| Q33 | A `@parameterize` row naming a parameter the function does not have raises `InvalidDecoratorException`, an `Exception` subclass that is not a `ValueError`, when the decorator is applied. | FIX | `ValueError`, also when the decorator is applied, listing every unknown row parameter, sorted, like every other malformed-function error. |
| Q34 | Every function node carries a `module` tag naming its module, beside the tags the author wrote; inputs carry no tags (`{}`). | FIX | A node's tags are only what the author wrote with `@tag`; its module is `NodeView.module`. Inputs carry no tags (`{}`) and their `module` is `None`, so the test compares inputs as `{}` on both sides. |
| Q35 | A `@parameterize` row binding a parameter that has a default to `source("x")` makes `x` optional, but when `x` is not supplied the node raises `KeyError` instead of using the default. | FIX | The keyword is left out, so the function's own default applies, exactly as for a plain optional parameter. |
| Q36 | `@tag` accepts a list of strings as a tag value, as well as a string. | KEEP / FIX | KEEP: a value is a `str` or a sequence of `str`. FIX: a `list` or `tuple` is stored as a `tuple` in written order, and `NodeView.tags` is a `Mapping[str, str \| tuple[str, ...]]`; an empty sequence or a repeated item is a `ValueError`, and a non-`str` item or an unordered collection (`set`, `frozenset`, `dict`) a `TypeError`, when the decorator is applied, naming the tag. Exports write a tuple as a JSON list and `diff` compares it in order. |
| Q37 | `tuple[int, ...]` is not treated as a generic: the input check rejects `(1, 2)`, and a node returning `tuple[int, ...]` does not feed a `Sequence[int]` parameter, because the `...` is compared as a second argument. | FIX | `tuple[T, ...]` takes a tuple, as `list[T]` takes a list (its items unchecked, as in Hamilton), and feeds `Sequence[T]`: across kinds its one element type is what is compared. |
| Q38 | A `NewType` over `int` takes no value (its values are plain `int`s at runtime, so even `1` is rejected), and a node returning it feeds neither `int` nor any type `int` would feed. | FIX | A `NewType` answers as its supertype: `1` fits it, and it feeds whatever its supertype feeds. Only the `NewType` itself (or `Any`) feeds a parameter annotated with it, as in Hamilton. |
| Q39 | A node returning `Literal[1, 2]` feeds only `Literal[1, 2]` and `Any`, not `int`, `object` or a union holding `int`. | FIX | A `Literal` producer answers as the types of its values: it feeds a parameter when each value's type does. |
| Q40 | A node returning a union (`int \| None`, `int \| str`) feeds only that same union and `Any`, not even `object`. | FIX | A union producer feeds a parameter when every member does, so `int \| None` feeds `object` and `int \| str \| None`; a union parameter still takes a producer that feeds one member. |
| Q41 | `Annotated[T, ...]` is checked by exact type in the input check, so `True` fits `int` but not `Annotated[int, "m"]`, and `Child()` does not fit `Annotated[Base, "m"]`. | FIX | Metadata never changes an answer: `Annotated[T, ...]` is checked as `T`, on both the input and the edge check. |
| Q42 | A parameter annotated with a plain (not runtime-checkable) `Protocol` and fed by a node returning a class makes the build raise the `TypeError` of `issubclass`, which names no node; a value that conforms to a `runtime_checkable` protocol is rejected by the input check. | FIX | A plain protocol cannot be checked at runtime, so it is no match (`False`), never an error; a `runtime_checkable` protocol takes any value that `isinstance` accepts. A plain-protocol input still takes no value, and not `None` either (Q79). |
| Q43 | The input check reads the first item of a value declared `Iterable[T]` to check it, so a generator or other iterator supplied as an input loses that item before the node runs, and is accepted or rejected by it. | FIX | An iterator is never looked inside: it is checked by its kind alone (it fits `Iterable[T]` and `Iterator[T]`, not `list[T]`), and reaches the node with every item. |
| Q44 | A PEP 695 alias (`type Price = float`) is compared as itself: the input check takes no `float` for a `Price` input, and a node returning `float` feeding a `Price` parameter, or returning `Price` feeding a `float` one, fails the build; the opt-out is the only way through, and it drops every check. | FIX | An alias is checked as what it names, read through any number of aliases, on the input and the edge check. A subscripted generic alias (`Pair[int]` for `type Pair[T] = tuple[T, T]`) is read with its arguments put in when its value is one of its type parameters or a generic over exactly those parameters, in order; any other generic alias answers as before. An alias nested inside another generic's arguments (`list[Price]` fed by `list[float]`) is compared as written on the edge check. Aliases naming each other are compared as written. Every alias's value is evaluated at build, so an alias over a name imported only for type checkers is unresolved, as any such annotation is (Q81). |
| Q45 | `Mapping[str, int]` takes no `dict`, `Callable[[int], int]` takes no function, and likewise every other parameterized abstract collection outside the `Sequence` and `Iterable` families (`MutableMapping`, `Set`, `Collection`, `MutableSequence`, ...): the input check refuses every value but `None`. | FIX | A parameterized `collections.abc` type outside those two families is checked by its kind alone, with `isinstance`, its items or signature unchecked; `Sequence[T]` and `Iterable[T]` keep the first-element check, and an iterator is still never read (Q43). The edge check already agrees with Hamilton on these forms (`dict[str, int]` feeds `Mapping[str, int]`) and is unchanged. |
| Q46 | F1, F2: the cache stores results by a hash of the value that ignores its type, so `1` and `"1"` share an entry: a node returning `"1"` gets back another node's `1` on the next run. | FIX | A result is stored by its node's key, which names the node, and an input's fingerprint carries its exact type and full structure: no two nodes, and no two values of different types, share an entry. |
| Q47 | F3: a value it cannot hash nested inside a container (a `__slots__` object in a list) is hashed as a constant, so the run hits after that object changed. | FIX | A value that cannot be fingerprinted at any depth makes the nodes reading it uncacheable: they run, and `explain_cache` gives the reason. |
| Q48 | F4: a node's code version is its own source only, so an edit to a helper it calls, or to a module constant it reads, still hits the old result. | FIX | The code version covers the function's code objects, the helpers and classes it reaches, the constants it reads, its defaults, closures and library versions; a global that may change makes the node uncacheable unless `@cache(version=...)` is given. |
| Q49 | F6: a `recompute` run does not replace the stored value, so the next default run serves the value from before the recompute. | KEEP | The same value: a node's policy is part of its key, so `default` and `recompute` never share an entry (a `recompute` result is not stored at all), and a default run after a recompute serves the earlier default entries for the node and everything downstream, consistently, never a recompute result beside downstream entries keyed before it. A node that reads the outside world must stay `recompute` (purity is declared). Pinned by `test_a_policy_switch_never_mixes_key_spaces` in `tests/test_caching.py`. |
| Q50 | F10, F11: `ignore` is set on the producer and drops it from every consumer's key, so a consumer hits after the producer's value changed; and the producer's result is still pickled, so a node producing a lock or a client fails the run with `TypeError`. | FIX | `@cache(behavior="disable")` on the producer never stores or versions its result; `@cache(ignore=("name",))` on a consumer leaves only that parameter out of that consumer's key, so it hits, while every other consumer still reads the producer. |
| Q51 | F12: a truncated or corrupt stored result fails the run with the unpickling error. | FIX | Entries are written atomically, and any entry that cannot be read is a miss: it is removed with a `CacheWarning` and the node recomputes. |
| Q52 | Something that is not a module, such as a function, passed to `Builder.with_modules` builds an empty graph, without error: the mistake surfaces at `execute` as an unknown output. | REFUSE | `build`, `Builder.with_modules` and the `Builder` constructor raise `TypeError: expected a module, got function 'f'`, naming the first item that is not a module (any `types.ModuleType` is one). |
| Q53 | A module that contributes no node builds an empty part of the graph, without error: a package whose `__init__` only re-exports functions defined in its submodules, a module of private helpers, or a hand-built `types.ModuleType` whose functions' `__module__` names another module. The user finds out at `execute`, as an unknown output (Hamilton issue #1281). | REFUSE | Build raises one `ValueError` naming every such module and each function it holds with why it is not a node: `'f' is defined in 'pkg.impl'` (a re-export, a node of the module that defines it) or `'_g' is private`; a module with no functions at all says so. Building from no modules at all is still an empty driver. |
| Q54 | `@cache(format="json")` stores a dict through a JSON saver that loads a tuple inside it back as a list, so the first hit returns a different value than the node computed, with no warning. | FIX | The built-in `json` format refuses any value that would not load back as the same types: a tuple, a set, a key that is not a `str`, a subclass such as an enum. The write is skipped with a `CacheWarning`, and the node runs again. |
| Q55 | `@cache(format=...)` naming a format no data adapter registers runs the node, then fails the run with `KeyError`, on every run. | REFUSE | Formats are resolved against the store when the driver is built. An unknown name, a `Format` unlike the store's of the same name, or a store that takes no formats is a `ValueError` naming each node. A `MemoryCache` holds values, never bytes, so it takes any format and ignores it. fnloom has no dependencies, so only `pickle` and `json` are built in: Hamilton's pandas-backed names such as `parquet` and `csv` are given as a `fnloom.Format`, or added to the store with `DiskCache(formats=...)`. |
| Q56 | Every config key becomes an input node: a parameter of the same name receives the config value, the key can be requested as an output, `inputs=` naming it is a `ValueError` ("present in both config and inputs"), and a key named like a function silently replaces that function with the config value. | FIX | Config shapes the graph and nothing else: a key is never a node, an input, a parameter value or an output. A parameter named like a config key is an ordinary input, supplied in `inputs=`; when it is missing, the missing-input error adds a line saying it is a config key, and config is not passed to nodes. A function named like a key stays a node. `Driver.config` is a read-only copy of the config. |
| Q57 | A config key the config does not have reads as `None`, so `@config.when_not(mode="a")`, `when_not_in` and `when(mode=None)` match an empty config. A node no variant matches builds as a required input, and the run fails at `execute` with `Required input foo not provided` (Hamilton issue #1213). | FIX | A condition on a missing key is false, whichever form it takes. A node no variant matches and with no `@config.default` is a `ValueError` at build when anything reads it: `no variant of 'foo' matches the config {'mode': 'c'}; its variants need mode == 'a' (foo__a), mode == 'b' (foo__b); add @config.default or a variant for it`, every such node listed, sorted. A node nothing reads is absent, and requesting it raises the same reason. A name that only a variant the config did not select gives, a row or an extracted field, is refused the same way, never made an input: `no selected variant gives 'r2': the config {'mode': 'z'} selects rows__other for 'rows', and only rows__a gives 'r2'`. An `@extract_fields()` naming no fields gives its `TypedDict`'s keys; when an unselected variant's return annotation does not evaluate at build, its fields are unknown and are not refused. |
| Q58 | Two variants of one node matching the config fail the build with `Cannot define function foo more than once`, naming the function added second, not the one already there. A config-decorated function defined twice in one module keeps the last definition silently. | REFUSE | Two matching variants are a `ValueError` naming both functions, sorted; two `@config.default`s for one node are refused the same way, whatever the config. A config-decorated function defined twice at the top level of its module is a `ValueError` naming it and the lines of each definition, read from the module's source at build; a module without source skips the check. A function bound under two names, or a module given twice, is one variant. |
| Q59 | `@config.when` without parentheses turns the function into a `config` object and the node silently disappears; a positional string is taken as the node name; `when_in(mode="ab")` tests substring membership, and a non-iterable fails at build with a bare `TypeError`; a name ending in `__` raises `InvalidDecoratorException` with a message cut off mid-sentence; and `when_not_in(name=...)` reads `name` as a config key while the other forms read it as the node name. | REFUSE | Each is refused when decorating: a bare `@config.when`, a positional string, a `str`, `bytes` or non-iterable for `when_in` and `when_not_in`, a name ending in `__` and a `when*` with no condition are a `TypeError` or `ValueError` saying what is wrong. `name=` is the node name on all four forms; a condition on a key called `name` goes in a positional mapping, `config.when({"name": "x"})`. |
| Q60 | Building renames the user's function in place (`foo__a.__name__` becomes `'foo'`, with `__original_name__` and `__config_decorated__` added), and every node from a config-decorated function gets a `hamilton.config` tag naming its keys. | FIX | The function is never changed, and no tag is added: a node's tags are only what the author wrote. `NodeView.config` holds the conditions that selected the node, empty for a plain function or a `@config.default`. |
| Q61 | `@extract_fields` checks nothing it declares: a field of the wrong type reaches its consumers, and `{"a": str}` on a `dict[str, int]` return builds. A field missing at run raises `InvalidDecoratorException`. Names given beside a mapping are dropped silently, a name a `TypedDict` return lacks raises a bare `KeyError`, a `Mapping[str, T]` return is refused, and two `@parameterize` rows under it fail only at build. An input declared as a `TypedDict` makes the input check raise `TypeError`. | FIX | Each field's value is checked on every run against its declared type, with the input check's matcher, even when input checks are off: a wrong type is a `ValueError` naming the producer, the field and both types. A declared type the return annotation can't feed fails the build, naming the field. A missing field is a `ValueError` naming the fields the producer returned, sorted. A mapping with extra names, a name the `TypedDict` lacks and two `@parameterize` rows are a `ValueError` when decorating. `Mapping[str, T]` returns are accepted. A `TypedDict` type, for a field or an input, takes any `dict`, its keys unchecked. |
| Q62 | `fill_with` writes the fill into the dict the producer returned, so the producer's own output changes, and so does a dict it returned from a module global. `fill_with=None` means no fill: a missing field still raises. | FIX | The fill is seen only by the field's node: the producer's value is never changed. `None` is a fill like any other; leaving `fill_with` out means no fill. |
| Q63 | `@tag` on an `@extract_fields` or `@extract_columns` function tags only the field or column nodes, not the producer, in either order. | FIX | The tags land on the producer and on every field or column node. |
| Q64 | `@extract_columns` needs a registered dataframe extension: with extensions not autoloaded, a `pd.DataFrame` producer fails at decoration with "does not output a type we know about". A `dict` return fails the same way even with the pandas extension loaded. A column named twice, as `"a", "a"` or `"a", ("a", "doc")`, fails the build with `Cannot define function a more than once`. `fill_with` writes the column into the producer's DataFrame, and with a `(name, doc)` column it adds a column named by the whole tuple, then fails with `No such column`. A missing column builds and fails at run with `InvalidDecoratorException`. A name the frame holds twice gives a DataFrame, and no column value is checked. | FIX | `extract_columns` is generic: it splits any value with `in` and `[]`, so it needs no extension, and a mapping works.
